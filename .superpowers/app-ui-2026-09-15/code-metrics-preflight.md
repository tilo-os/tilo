# Code Editor Task 13 source preflight

Scope: read-only review of the current Task10-accepted source. No production/test edits, build, test run, or capture was performed. The existing `task10-code-final-20260916/captures/code_editor/large-text.png` is the visual evidence for fixed-row overlap.

## Current ownership and failure mechanism

- `EditorView` owns all editor geometry. `FONT_SIZE=14`, `LINE_HEIGHT=20`, `FALLBACK_CELL_W=8.4`, `GUTTER_PAD=12`, and `CODE_PAD_LEFT=12` are declared at `editor_view.rs:90-101`; only `cell_w` is retained (`EditorView.cell_w`, `:148-149`). `draw()` measures `M` at the renderer-relative 14 px size (`measure_cell_width`, `:1330-1338`) before painting.
- `TextRenderer` already applies its accessibility scale to literal styles in both `measure_style` and `draw_style` (`ui/src/text_render.rs:1402-1446`, `:1540-1563`, `:1906-1924`). Thus `cell_w` grows at 2x, but `LINE_HEIGHT` and the surrounding geometry do not. This exactly explains enlarged glyphs overlapping on the old 20 px pitch.
- The fixed pitch is independently consumed by visible-row count and caret scrolling (`visible_lines`/`scroll_to_caret`, `editor_view.rs:699-730`), point-to-caret (`:1314-1325`), line/find/selection paint (`:1341-1477`), line-number/source paint (`:1480-1604`), diagnostics and carets (`:1607-1709`), completion/hover anchors (`:1720-1893`), pixel-wheel conversion (`:2010-2022`), Page Up/Down (`:2131-2194`), draw-time caret anchor (`:2462-2484`), and test inverse geometry (`:2644-2659`). The completion popup also has its own fixed 20 px row (`:1730`); hover line advance and the horizontal-scroll recovery chip are separately fixed (`:1856-1889`, `:2293-2329`).
- `layout_metrics()` is only a draw tuple and is not authoritative outside paint. Hit testing, scrolling, popup placement, and accessibility therefore cannot share it.
- `BottomPanel` owns fixed outer choices of 160 px and 216 px (`bottom_panel.rs:23-35`, `height()` at `:157-164`). Its 30 px tab, 20 px problem row, 26 px search row, fixed baselines, search budget, tab hit strip, and terminal `content_rect()` are separate constants/offsets (`:166-172`, `:212-387`, `:432-440`, `:471-638`, `:749-869`). The renderer enlarges the 11/12/13 px labels, while those bands stay fixed.
- `CodeApp::build_editor_column` keeps the editor as the flexible remainder and conditionally inserts the panel (`app.rs:3574-3681`). Task10's retained same-row trigger, default-collapsed state, canonical command routing, terminal close/focus handling, and child gating are already localized in `app.rs:91-351`, `:2677-2714`, `:3574-3681`, `:3998-4078`, and `:4779-4805`.

## Smallest implementation shape

### 1. One editor metric snapshot

Replace `cell_w` plus the scattered constants with a small `EditorMetrics` value retained by `EditorView`. It should contain at least the effective scale/font size, line height, monospace cell advance, text inset, gutter padding/width inputs, and code-left padding. Keep one base monospace `TextStyle` at 14 px with an explicit `20/14` line-height multiplier. This preserves the current 1x pitch while letting the same style measure to roughly 40 px at 2x.

Before first draw, `build_layout(theme, ...)` should install a deterministic fallback from `theme.text_scale`: `14 * scale` font size, `20 * scale` line pitch, and `8.4 * scale` cell advance. The first draw should refine the snapshot using `TextRenderer::measure_style("M", ..., same_style_used_to_draw)`. If the snapshot stores a fully resolved size, normalize it with `renderer_input_style`; do not multiply a literal size by `theme.text_scale` and then pass it to a renderer that scales again. Keep the authored 12 px paddings as normal minima rather than scaling every gap blindly.

Resolve/refine the snapshot before any draw geometry is computed. On change, atomically replace it, clear/rebuild derived rect caches, and mark geometry/redraw dirty. Do not call `bind`, rebuild the document cache, move carets, or reset selection/scroll. Vertical scroll is already expressed in logical lines, so it naturally survives. Horizontal scroll remains pixel-valued; either retain it exactly or convert it once to a cell-column anchor, but do not run `scroll_to_caret` merely because measurement refined.

Add pure helpers such as `line_rect`, `caret_rect`, `column_x`, `point_to_caret`, `visible_line_range`, `diagnostic_rect`, and `completion_rect`. Drawing, wheel/page movement, ensure-visible, find/selection bands, diagnostic squiggles, hover/completion anchors and rows, the horizontal recovery chip, test aiming, IME candidate geometry, and any synthetic semantic rows should consume those helpers. This is smaller and safer than threading another tuple through every paint function.

### 2. Bottom-panel metrics without changing pane choices

Retain `PANEL_HEIGHT=160` and `PANEL_HEIGHT_SEARCH=216`; these are the existing fixed pane choices and scaling them would unnecessarily take code height, especially in the short viewport. Add a `PanelMetrics` snapshot for measured tab height, summary/hint bands, problem/search row heights, baselines, and horizontal label extents. Automatic bands should use `max(existing 1x minimum, measured occupied height + existing padding)`. Fewer rows should fit at large text.

Recompute width-dependent search-summary and diagnostic-message height with the same style/weight/width used to paint. Search result rows can remain single-line and ellipsized, but their measured row rect must drive drawing, wheel row budget, hit rects, and click-to-result mapping. Problem rows may become variable-height if the existing wrapped message is preserved. Rebuild `tab_rects`/`hit_rects` from the resolved metrics every draw.

`content_rect()` must start below the resolved tab strip. The app already draws the panel before placing the live terminal (`app.rs:4483-4488`, `:4542-4549`), so a refined tab metric can feed the terminal in the same frame. Keep the live terminal as the sole owner of that body; do not paint fallback text underneath it or recreate the terminal when metrics change.

Switching between Search and Problems/Terminal changes the fixed outer choice, but `BottomPanel::set_tab` currently only sets `dirty`, and `CodeApp::take_structure_dirty` only reports docked-sidebar animation (`bottom_panel.rs:460-469`, `app.rs:5101-5108`). Add an edge-triggered panel structure signal when the height class changes and OR it into `CodeApp::take_structure_dirty`; this is the only app layout integration needed beyond preserving Task10 behavior.

### 3. Scale/theme, IME, and semantic boundaries

- `CodeApp::active_theme` replaces a user-selected palette with a fresh unscaled theme (`app.rs:983-994`) while the retained `TextRenderer` still has the host scale. Any metric code must treat renderer scale as the draw-time authority. Narrowly preserve the host `text_scale`/`ui_scale` when constructing a selected color theme, or custom theme cycling will reintroduce measurement/paint disagreement for token-based content such as `EmptyState`.
- `EditorView` currently has no `wants_tab_input`, `ime_cursor_rect`, or `WindowEvent::Ime` path; the host therefore disables native IME for it (`Widget::ime_cursor_rect`, `ui/src/widget/mod.rs:838-852`). Do not claim IME coverage from the metric repair alone. The smallest complete addition is a metric-derived caret rectangle plus preedit/commit state: preedit paints at the caret without document mutation, Commit uses the existing action-owned `insert` route, Disabled/focus loss clears preedit. Returning an IME rect without handling IME events would enable a broken input path.
- Current accessibility is only a retained `Role::Document` named “Code editor” (`editor_view.rs:2573-2583`); its whole-widget bounds come from `get_rect`. There are no metric-sensitive semantic bounds today. To satisfy the brief without redesigning editable accessibility, expose only visible source lines as stable-key synthetic `StaticText` children using the same clipped `line_rect` helper. If acceptance instead expects `MultilineTextInput`, value/selection and SetSelection/ReplaceText actions, that is a separate interaction expansion and should not be implied by this task.

## Concrete risks and exclusions

- Do not cherry-pick or reproduce `cba6d9c75` as-is. That experiment multiplies font sizes by `theme.text_scale` before calling a renderer that now scales them again, scales whole panel heights, and does not close the IME/semantic gaps.
- The editor's char-column/fixed-cell model still cannot exactly represent combining marks, double-width glyphs, or tab shaping. Task13 can make its existing monospace model scale-consistent; a shaped per-line caret map would be an editor redesign.
- Completion and hover are paint-only overlays, and panel tabs remain pointer-only internally; palette commands are the existing keyboard route. Do not claim new accessible activation unless corresponding semantic/action routing is actually added.
- Preserve Task10's collapsed default, same-row toggle, canonical command path, selected panel tab, terminal object/focus cleanup, and conditional child exposure. Metric refresh is view geometry only and must not enter replicated document state.
