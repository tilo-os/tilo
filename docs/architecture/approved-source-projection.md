# Approved checks of current collaborative source

An approved check can compile a fresh source candidate from the Code Editor's
committed document snapshots. Its public action still takes only `check_id`.
Commands, images, filesystem paths, source mappings and resource bounds come
from the trusted compositor startup configuration, `--approved-checks PATH`.
The registry remains empty without that configuration. There is no public
arbitrary-command registration action or owner registration UI in this increment.

Each optional `source_projections` entry names one already approved check, the
SHA-256 of its reviewed baseline file inventory, and a closed set of replacement
paths. A replacement binds an exact application, workspace, canonical record,
resource semantic identity, read action and file ID. The host resolves the
current publication rather than reusing an opaque resource address from a
previous app process. The accepted check's original opaque address and target
connection continue to bind that invocation's custody.

## Admission and snapshots

The check host retains the broker's genuine original invocation. A nested read
uses the original Person admission or the accepted native Agent's current task
run and lease. An Agent cannot fall back to a Person, Host or worker origin.
Both the accepted check and each independently Read-authorized source operation
must remain current. The source target applies its ordinary resource permissions
and immutable document reader. Cancellation, revocation, changed publication,
retired process or unknown terminal outcome refuses the candidate.

Source chunks contain one canonical record and one sorted committed head set.
Every subsequent chunk requests those same heads; files sharing a record also
share the same captured head set. Positions are Unicode scalar values. Chunk,
file and aggregate byte limits apply, and the collector checks the full text
hash after contiguous collection. These are projection-time committed heads,
not a claim about the document heads when the parent check was admitted.
Original invocation IDs and live broker guards establish the local observation;
the JSON payload and its hashes are not portable authority or a signed snapshot
certificate. Canonical record metadata follows the existing SDK contract and
may contain device-local identifiers.

## Fresh candidate and execution

The host verifies the reviewed baseline inventory, rejects history, symlinks,
path escapes and nonempty source build directories, then exclusively creates a
new private candidate for the actual check invocation. Only approved replacement
files change; other baseline files retain their bytes and owner executable flag.
An empty `target` mount point receives a distinct writable build directory.
There is no shared mutable build target and no fallback to checking the baseline
when source collection fails. Empty directory layout and full POSIX modes are
not part of the file inventory identity.

The existing `ush` approved-check supervisor runs the same fixed command and
image with its enforced CPU, memory, process, time, output and network bounds.
Source guards remain live before and during execution. The host verifies the
candidate inventory before and after execution and rechecks custody before
returning a receipt. Private provenance retains the baseline and candidate
inventories, actual child terminal observations, heads and executing check.
The optional public `candidate_source_sha256` identifies the actual candidate
file inventory; it does not replace that private provenance. Legacy static
checks omit the field and preserve their existing receipt encoding.

This projects an evaluation candidate; it does not save the live editor buffer.
Save, Save As and Save All retain their existing device approval and filesystem
permissions. An exited command is also not automatically a coding-quality
score: an evaluator must observe its named grader outcomes and bind the actual
candidate, model and harness identities separately.
