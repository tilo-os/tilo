# CPU-prefix feasibility: defer selective flatten

Read-only follow-up, no source change/build/runtime. Existing selective CPU pathtag/metadata/draw-prefix stages are already defaults, not new savings.

A selective CPU flatten boundary is possible before the GPU suffix: config/scene still have host transient bytes, CPU pathtag monoids are host-resident, and bbox_clear is already eligible CPU metadata. CPU flatten could produce path_bbox, bump and lines before draw_leaf_prefix. The engine's CPU-to-GPU transition is one-way (wgpu_engine.rs upload_if_needed around 3047); create_cpu_resources rejects resources already GPU-materialized (around 3341). Existing upload commands eagerly send config/scene to GPU while retaining host transient bytes, so this proposal would not remove those existing uploads. New host-produced lines/bump would incur uploads, and generic host lines allocation is not covered by the current three retained CPU pools. One first-consumer upload per output is not zero-copy or proof of lower memory traffic.

It is not safe as a plumbing-only switch:

- GPU flatten uses atomic reservations for LineSoup ranges (flatten.wgsl around 512, 536, 595, 783–800); CPU flatten serially walks tags (cpu/flatten.rs around 675–844). Cross-invocation physical line order is not deterministic, so exact whole-LineSoup-buffer equality is not a valid general gate. A logical bit-pattern multiset, per-path bbox and bump.lines comparison can be structural evidence only; strict downstream full/sparse pixel oracles remain necessary.
- CPU/GPU geometry math is not identical: WGSL transform uses explicit FMA (flatten.wgsl around 668–671); CPU Transform uses separate arithmetic (cpu/util.rs around 144–148). Rust and WGSL transcendental operations also differ. Exact numeric geometry/pixel parity has not been established. No new tolerance or canonical ordering is authorized.
- GPU write_line bounds-checks line_ix against config.lines_size while still advancing requested line counts (flatten.wgsl around 768–774). GPU binning detects excess lines and records STAGE_FLATTEN for existing retry handling (binning.wgsl around 64–74). CPU write_line directly indexes lines[line_ix] (cpu/flatten.rs around 76–96), so capacity exhaustion can panic before normal recovery. A bounded non-panicking writer and matching overflow semantics would be new correctness work.
- Extending to CPU clip/binning/tile allocation is broader still: CPU clip_leaf explicitly says it does not rigorously follow WGSL, and moving later CPU stages after GPU-produced predecessors requires invalid residency or new readbacks. Neither is acceptable for this small candidate.

Cold-cache qualification: synchronous CPU flatten executes before queue submission/fence waiting. Added CPU work may increase initial-paint wall time, but it is incorrect to assume it directly consumes the one-second GPU fence budget. It is also not proven to resolve the observed Mesa first-use misses/failures; moving one stage cannot be presented as a cold-cache remedy without testing.

Decision: defer CPU flatten implementation. Investigate a narrower all-GPU clip-leaf single-workgroup specialization that preserves existing arithmetic/ordering and can remove the provably empty prefix-stack work for group zero. This is a feasibility audit only; no implementation/default promotion yet.
