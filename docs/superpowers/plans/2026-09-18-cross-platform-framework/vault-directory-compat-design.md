# Task 7 — legacy vault directory and key admission

2026-09-18. Approved bounded compatibility contract for the ordinary Unix legacy profile; implementation awaits Task5 shared reconciliation. Windows namespace admission and broader native qualification remain unresolved. Source inspection and this design artifact only; no product edits, builds, tests, or native qualification. Task 5's shared existing-file commit and Task 4's Windows directory work remain dependencies. This does not design credential transport or change custody.

## Recommendation

Preserve ordinary legacy vaults **in their current directories**. An effective-user-owned `0755` directory with a private, single-link `0600` key does not require chmod, key replacement, or relocation. Directory listing/search permissions disclose names; they do not themselves grant permission to change directory entries. Private key contents and exclusive control of the containing namespace are different requirements.

Add one framework-owned held-directory **namespace-control validator**, separate from `Privacy`. Use it for existing vault directory admission. Continue using `OwnerOnly` without changes for the key, for newly created directories, and for callers that expressly require private directories. Do not reinterpret `OwnerOnly` as “no foreign writes,” or add a permissive fallback after its validation fails.

This is an explicit compatibility policy: existing vault directory names may remain visible; key contents must be owner-only; publication requires an owner-controlled namespace plus the framework's existing trusted-host/cooperative-owner premise. New directories remain private. No persistent “legacy” flag, version marker, sidecar, alternate path, native logic in accounts, or OS branch in accounts is needed.

## Source facts

* `crates/system/accounts/src/vault.rs::try_save` calls ordinary `create_dir_all`, obtains its selected key, then seals and replaces `vault.enc`. `write_key_file` uses `write_with_mode(..., 0600)`. Thus the old contract did not promise a `0700` vault directory. Existing `vault_put_save_load_round_trips` and `key_file_is_owner_only` test the current location/format and key privacy, not directory privacy.
* `local_file_key` currently uses unbounded ambient `fs::read`, accepts any 32-byte result, and regenerates on every read error. `secret_service_key` has another ambient local-key read during migration. Both local-key read routes need the same held validation; Secret Service lookup errors must continue refusing local fallback.
* `StorageDirectory::open_read` already performs relative no-follow, regular-file admission and `OwnerOnly` validation. `FileIdentity::of` queries the actual returned handle. Native file privacy rejects additional hard links. Unix directory privacy uses the supported permission-profile check and requires effective owner plus no group/other permission bits; macOS additionally checks extended ACLs. Windows private security requires effective principal, protected DACL and no foreign allows.
* `provision_directory(OwnerOnly)` intentionally rejects an existing nonprivate leaf. Existing traversal ancestors need not be private. It retains complete-chain authority, preserves directory effects, and commits leaf-to-root. Its `Inherit` policy alone does **not** establish namespace control.
* The approved Task 5 design proposes `reconcile_directory(path, expected_leaf, privacy)` and `commit_existing(name, expected_identity, privacy)`. The latter flushes the actual existing file/name without replacing it. Reuse these seams; accounts must not implement another fsync/open/ACL engine.

## Minimum API addition and its scope

Proposed addition in `atomic-file`, with native implementation beside existing privacy admission:

```rust
impl StorageDirectory {
    pub fn validate_namespace_control(&self) -> std::io::Result<()>;
}
```

The method inspects the held directory, never changes permissions, never creates anything, and never treats inability to inspect as success. Require a supported native enforcement profile, effective-user ownership, and no untrusted-principal authority to mutate the directory's namespace or security. Owner read/write/search permissions can still be inadequate for the requested operation; return the actual native access failure rather than repairing them. A successful validation is current admission, not a durable certificate or permanent lease.

For the first bounded Unix implementation:

* On the existing admitted Linux POSIX-DAC profiles, require effective-user ownership and `(mode & 0o022) == 0`, retaining the profile/trusted-backing requirement. Group/other read and search are allowed. Reuse the established permission-profile logic rather than treating every filesystem as mode-enforcing. Named access-ACL write must be covered by the profile's ACL mask semantics and real fixtures. Default ACL inheritance is a separate private-child-creation obligation.
* On macOS, apply the same ownership/mode namespace check **and reuse the existing conservative extended-ACL validator**. This admits ordinary `0755` with no foreign allow ACL, owner allows, and benign denies. It rejects foreign allow entries even when potentially harmless; this is a documented initial ACL-profile limit, not an assertion that every foreign read ACE permits mutation. No new partial ACL evaluator is justified solely to accept the common legacy mode case.
* Do not apply the file single-link rule to directories. Do not require every ancestor to be owned by the effective user or have private mode. Do not use this method for key-file privacy.

Namespace admission never bypasses or substitutes for any current OwnerOnly creation check. The immediately usable legacy profile is owned `0755` (or the other admitted nonwritable modes) with no additional foreign allow ACL, plus the existing supported owner-allow/deny cases. On macOS the current conservative OwnerOnly **directory provisioning** preflight rejects foreign allows even when noninheritable; preserve that behavior. File publication instead validates the actual staged child's privacy before writing bytes; it does not call that directory preflight. Test these distinct production checks separately. A noninheritable foreign-read parent ACL can leave a staged file private while still failing the vault's conservative namespace admission. Do not relax either check, create broadly and repair, or route private creation through Inherit to make this compatibility path succeed.

If qualification finds actual supported legacy macOS directories with foreign **read-only** ACLs, admitting them is an expansion of the framework's supported namespace ACL profile, not a reason to chmod them. Any future expansion must distinguish effective namespace/security mutation permissions and inheritance scope; unsupported or uninterpretable entries fail. Merely expanding namespace admission would **not** establish that such roots can initialize a private key, create private descendants, or complete all save paths: existing private-from-creation preflight remains independently binding. No new ACL creation engine is proposed in this increment, and no general read-only-ACL save compatibility is claimed.

On Windows the same semantic method needs its own finite native implementation and fixtures before Task 7 is portable. Do not reuse the current private-DACL predicate as the final namespace-control policy: an inherited or foreign-read directory DACL may control its namespace safely while failing that stronger privacy predicate. Conversely, testing only file data-write permissions misses namespace/security mutation authority. See the native evidence section below.

The method does not defeat hostile same-principal processes, privileged principals, mount changes, mutable backing aliases, or a foreign-writable ancestor capable of rebinding the path. The existing trusted host namespace and cooperative owner maintain exclusion and ACL stability throughout the operation. Held handles and binding checks preserve/detect authority; they are not hostile-path confinement. Revalidate namespace control before sensitive child effects, before returning key authority for a save, and around an owned retry. Accounts calls the shared validator; it does not reproduce its native tests.

## Admission and operation order

Keep accounts' parsing, crypto and custody selection shared. Its small private preparation helper can compose the framework calls; it must not select native implementations.

### Existing read / load

1. Open the existing directory as a held `StorageDirectory`; validate namespace control. No provisioning, chmod, key generation, or durability write is needed merely to decrypt an existing vault. Preserve the current path/alias policy under the trusted-host premise.
2. Open `vault.key` relative to that directory with `OwnerOnly`, retain the returned file and its full `FileIdentity`, and read at most `KEY_LEN + 1` bytes into zeroizing storage. Require exactly 32 bytes, including EOF; do not trust only a pre-read length. Reject symlink/reparse, nonregular, additional-link, owner/ACL, malformed, and read errors without another read route or fresh key generation.
3. Read the existing ciphertext relative to the same admitted directory. Its legacy inherited file privacy is not silently upgraded as a prerequisite to decryption. Keep `QASV`, version 1, the 24-byte nonce and AEAD interpretation unchanged. Returning an empty public view on a failed load must not become evidence that an old vault is absent or permission to create a replacement key.
4. The Secret Service **existing local-key migration read** must call the same admission/read helper. It may still follow its already-selected custody path. This design does not change lookup/store verification/removal, add fallback, or certify that separate transport/removal protocol.

### Save / durable key acquisition

1. If the directory exists, open it, validate namespace control, and call Task 5's **existing-only** `reconcile_directory(path, &held, Inherit)`. `Inherit` here preserves existing directory permissions; namespace validation supplies the separate exclusion premise. Revalidate namespace/binding after reconciliation. No mkdir or permission repair occurs on this branch.
2. Only a proven missing directory may enter `provision_directory(path, OwnerOnly)`. Keep its private creation, winner validation, full-chain barriers and typed errors unchanged. Validate namespace control on the returned held directory. A race where an old process creates a nonprivate leaf may cause this attempt to fail; do not reinterpret that failure or discard earlier effects. A fresh invocation can admit that now-existing leaf through step 1. This avoids a mixed creation/adoption policy in the provisioner.
3. Read an existing key through the held helper. Before it can authorize new ciphertext, use Task 5's `commit_existing("vault.key", &observed_identity, OwnerOnly)`, then revalidate namespace/binding. The earlier directory reconciliation plus this existing file/name commit supplies the required composition; no duplicate native durability implementation or byte-equality shortcut belongs in accounts. Read-only load need not require the writable handle that this save-time commit may need.
4. Only proven key NotFound is eligible for generation. It is not sufficient if an existing local-custody ciphertext requires the missing key: preserve that orphaned vault and return unavailable/error for explicit recovery. Query/read failures must not be mistaken for empty first launch. Generate only for established first initialization, then publish `vault.key` with `IfAbsent + OwnerOnly` through the held directory.
5. After a real collision, zeroize/discard the losing candidate and read/admit the actual winner through step 3. `AlreadyExists` alone is not proof of a target winner because staging exhaustion can report it. Neither matching bytes nor a successful read proves that an earlier publisher committed the name.
6. A known `PublishedDurabilityUnknown` may retry its retained commit boundedly, while namespace authority remains admitted; only successful commit plus winning binding validation releases the selected key to encryption. `PublicationUnknown` does not authorize commit-only retry, deleting a possible winner, overwriting, or returning generated bytes. Return the diagnostic, or perform the complete independent existing-winner protocol if parent authorizes same-call reconciliation. A later fresh invocation always repeats normal admission and real barriers. Directory partial/unknown states retain their distinct effects and likewise prevent key/ciphertext publication.
7. Only now seal and publish ciphertext using semantic held publication. Keep `try_save`'s `Result<(), String>` compatibility, include the failure phase in diagnostics, and preserve downstream account-metadata ordering. No failure is translated into key regeneration. A failure after ciphertext publication may leave new bytes visible and still returns failure.

The missing-key/existing-ciphertext guard is a narrow read-admission requirement, not new credential custody. Parent should make it explicit in the Task 7 brief because current `load_entries` calls the create-capable helper while opening old ciphertext. Split read-only selection from first-initialization acquisition instead of carrying that unsafe behavior into the new helper.

## Compatibility versus actual migration

| Observed legacy state | Result |
| --- | --- |
| Owned `0755`, `0750` or `0711` directory; valid private single-link key; supported native profile | Admit in place, decrypt and save; leave permissions, key bytes/identity and location unchanged. No migration. |
| Existing `0700` directory and valid private key | Same path; privacy and namespace policies both happen to hold. |
| Empty owned namespace-controlled legacy directory | Can initialize a new private key after proven absence; no chmod needed. |
| Missing directory tree | Create private directories through Task 4; never create broad and repair afterward. |
| Foreign-writable namespace, untrusted owner, or namespace-changing ACL | Refuse automatic admission and preserve all data. Safe ownership/exclusion must be established before an explicit recovery or permissions transition. |
| Key itself readable by another principal, malformed, hard-linked or untrusted | Refuse automatic key admission; do not chmod-to-pass, replace, import blindly, or infer that confidentiality can be restored retroactively. |
| Directory namespace-safe but outside the implemented ACL profile | Keep native-profile qualification as concrete unfinished work; do not advertise full legacy support or prescribe unnecessary permission changes as the final answer. |

Moving `0755` to `0700` would add name confidentiality. It is a new policy choice, not a technical necessity for keeping a `0600` key private. If product explicitly requires it, design and authorize an in-place, held-identity permission migration separately, preserving restart/concurrency and metadata durability; do not sneak it into provisioning or fixture setup. Truly unsafe namespaces may need such a transition to establish exclusion, but a chmod cannot prove old key secrecy or old ciphertext provenance. Full key recovery/rotation is outside this bounded design. Ordinary legacy usability is resolved by admission, not deferred to that recovery work.

## Required exact tests

Tests must call production admission/public save paths and observe real framework checkpoints; no synthetic durability visits, weakened OwnerOnly assertions, skips, or fixture hardening in the migration path.

1. Construct a genuine old-layout fixture using the old ordinary-directory/private-key writer semantics (isolated subprocess umask `022`, `create_dir_all`, private 32-byte key, version-1 encrypted known credential). Verify `0755` **before** new code runs. Reopen, decrypt, mutate, `try_save`, reopen again. Assert directory mode/ACL unchanged, key bytes and native identity unchanged, path unchanged, version preserved and old/new credentials present. Do not chmod this fixture to `0700`. Retain original round-trip and key-mode baselines unchanged.
2. Directly prove policy separation: that same held `0755` directory fails `validate_privacy(OwnerOnly)` and passes namespace control. `provision_directory(..., OwnerOnly)` still refuses it without mutation. Cover `0750`, `0711`, `0700`, wrong owner and group/other-writable directories; configure each initial fixture deliberately and assert no production permission rewrite.
3. Native cross-principal fixture: the second nonprivileged principal can observe allowed names but cannot read the key or create/rename/unlink children. For admitted Linux ACL profiles, a named-user write ACL is rejected, while a read/search-only ACL consistent with the profile's mask is admitted. A unavailable second principal/ACL facility is missing qualification, never a passing test.
4. macOS: plain legacy mode fixture succeeds; owner allow/benign deny fixtures retain current supported behavior; foreign allows fail conservatively without mutation. Record separate unfinished qualification if harmless foreign-read ACL support is needed. Inheritable ACL cases must prove no private bytes are written before key child privacy is established.
5. Symlink/reparse key, FIFO/directory, hard link, foreign owner, permissive key, lengths 0/31/33/oversized, permission-denied and injected read/query I/O failure: no RNG/key publication/ciphertext publication, no permission changes, original identity/bytes preserved. Exact 32-byte bounded read succeeds. Exercise both local custody and the existing Secret Service local-key migration read helper, with no lookup-failure fallback.
6. Read-only load on an admitted legacy vault performs no mkdir, key publication or commit operation. Missing key with existing ciphertext refuses generation and preserves ciphertext. Missing ciphertext with an inaccessible/unproven state is not absence. First initialization under absent roots still provisions and saves successfully.
7. Existing legacy key save observes actual shared existing-file/name commit and full ancestry reconciliation. Fault each separately: no encryption/ciphertext or dependent metadata publication. Drop the first error and reopen in a fresh process: actual barriers execute again, key identity/bytes survive. An existing read success does not acknowledge save durability.
8. Two actual processes initialize the same admissible legacy directory: one immutable key winner, both select that validated durable key, no losing candidate escapes. Inject known final commit failure and ambiguous publication: no ciphertext until the corresponding owned retry or independent reconciliation succeeds. Replacing the key with equal bytes between read and existing commit fails identity admission.
9. Directory/alias replacement and permission change at real admission/commit checkpoints fail without rebasing, creating a replacement source, or chmod/cleanup. Owned retries revalidate namespace as well as the existing shared binding/privacy obligations. A provision failure followed by a fresh existing-directory attempt preserves typed effects and repeats barriers.

## Tradeoffs and native evidence still owed

The chosen seam adds one permission predicate, retains all existing publication/durability machinery, and restores the dominant real legacy case without format migration. A combined “create private, adopt namespace-controlled” provisioner policy would handle an old-binary creation race in one call, but expands Task 4 state/retry semantics unnecessarily; bounded failure followed by fresh admission is adequate. Silently hardening directories changes policy and introduces metadata migration obligations. Relocating the vault or changing custody breaks the stated compatibility boundary.

Linux needs actual ACL/profile and second-principal fixtures; this source review did not independently qualify ACL enforcement. macOS's current conservative ACL parser is enough for the ordinary no-foreign-ACL legacy fixture, not evidence for admitting all namespace-safe extended ACLs.

Windows needs a framework native namespace admission implementation that accounts for directory child creation/deletion, deletion/rebinding/security modification authority, generic-right mappings, inheritance, principal identity, and unrecognized ACE forms. Current `validate_private_security` intentionally does not answer that question. Native fixtures must include ordinary inherited legacy directory ACLs, read-only foreign access, foreign namespace mutation, and private key validation without weakening OwnerOnly. Any legacy key that itself fails private-file admission is a separate explicit recovery case, not a reason to change the directory predicate. Verify supported legacy Windows artifact shapes from actual old writer behavior rather than assuming POSIX `0600` describes their ACLs.

Windows first launch and existing-winner durability also still depend on Task 4/5's selected native namespace barrier and lost-error/restart evidence. Namespace admission does not settle either. Complete those finite framework implementations and native fixtures before claiming Windows Task 7; neither a permanent Unsupported branch, compilation, nor this design closes them. No new ACL web claims or native experiments were used to manufacture certification here.
