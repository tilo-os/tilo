# Windows directory commit: evidence and bounded probe

2026-09-18. Scope: Task 4, unprivileged Windows 11 on local NTFS. No Windows execution was available. This report specifies a candidate and qualification work; it does not certify power-loss durability. Existing regular-file publication work can proceed independently.

## What primary documentation establishes

- **Write-through directory handles are explicitly allowed.** User-mode [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) creates directories relative to `OBJECT_ATTRIBUTES.RootDirectory`. `FILE_DIRECTORY_FILE` expressly permits `FILE_WRITE_THROUGH` and `FILE_SYNCHRONOUS_IO_NONALERT`; permitted dispositions include `FILE_CREATE` and `FILE_OPEN`. Synchronous opens require `SYNCHRONIZE`. A supplied security descriptor applies at creation. `IO_STATUS_BLOCK.Information` distinguishes creation from opening. The page describes directory structures being created on disk, but does not explicitly promise durable completion of their parent entry. Its directory-option whitelist omits `FILE_OPEN_REPARSE_POINT`, although the same page documents that option generally: qualify the exact combination rather than silently dropping no-follow protection.
- **There is a documented metadata connection.** [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) says an NTFS write-through request also flushes resulting metadata changes, including rename. This supports investigating a write-through directory rename; it does not explicitly specify the native directory-create request's parent-index flush. `CreateFileW` itself opens existing directories with backup semantics; it cannot create one. Write-through depends on storage hardware honoring the request. `FILE_FLAG_WRITE_THROUGH` is the Win32 flag; native `FILE_WRITE_THROUGH` uses a different value.
- **Normal native flush has the strongest stated scope.** [NtFlushBuffersFileEx](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntflushbuffersfileex) with flags `0` writes cached data and metadata and synchronizes underlying storage. The function is synchronous. Its data-sync-only mode explicitly excludes directory handles; normal mode has no such exclusion. This is positive evidence for testing normal directory flush, not an explicit promise that flushing a child also commits its parent entry. Access-denied is documented for handles lacking write/append access. The page documents a driver entry point; user-mode `ntdll` export availability/support must also be recorded, not inferred from the kernel requirements table.
- **Directory access bits have directory meanings.** [File access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-access-rights-constants) assigns `FILE_ADD_FILE=2` and `FILE_ADD_SUBDIRECTORY=4`, the same bits as file write/append. These rights provide a concrete unprivileged flush-access probe. Do not request generic file rights merely because native-create prose uses file terminology. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) requires `GENERIC_WRITE`; whole-volume flushing requires administrative privilege and is not the application protocol.
- **Handle-relative rename exists, with directory restrictions.** [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) supports a destination root handle, requires source delete access, and restricts renames to one volume. Directory targets cannot be replaced; open handles in directory trees impose restrictions. Test an empty stage before opening descendants. The root-handle sharing guidance matters even when all paths are private. These rules establish namespace mechanics, not a separate crash guarantee.

## Candidate to implement after the bounded probe

Start from an admitted existing parent whose own durability is established externally or by the same protocol. Hold that parent throughout. Create an empty private staging directory relative to it, validate the created handle, then rename the stage to the desired absent component using the held parent. Retain the same child handle and normal-flush child, then parent. Only after both complete may the new component be used as the durable parent for the next component. Publish application files after the entire missing ancestor chain is committed.

The proposal deliberately commits each empty component before descendants exist. It avoids the documented open-descendant rename restriction and makes the ancestor obligation explicit. Also probe direct exclusive final-name creation followed by child/parent flush: it may be the simpler sufficient protocol if native evidence establishes creation semantics. Directory existence can become visible before durable success; neither candidate promises a transaction over the entire hierarchy.

**Inference needing qualification:** combining directory write-through, NTFS's dependent-metadata rule, and normal child-plus-parent flushing commits both the new directory object and its namespace link. Neither API success alone nor a successful crash sample upgrades this into an unconditional guarantee for all storage stacks. Record the supported OS/filesystem/storage assumptions and obtain directory-specific Microsoft clarification if the project's promised guarantee requires a stronger documented contract.

## Exact native probe specification

Use a standalone test executable, standard-user token, no enabled backup/restore/manage-volume privileges, no production environment switches. Initially test Windows 11 x64 and arm64 on local NTFS. Log OS build, architecture, token elevation/privileges, storage/cache configuration, filesystem name/flags, and all native results.

1. Hold a test parent. Query `GetVolumeInformationByHandleW`; require NTFS. Query `FileFsDeviceInformation`, recording `DeviceType` and `Characteristics`; reject remote characteristics. [FILE_FS_DEVICE_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_file_fs_device_information) exposes these fields; [DEVICE_OBJECT](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_device_object) defines `FILE_REMOTE_DEVICE`. Query failure is inconclusive, never evidence of locality. Record `FileIdInfo` volume serial/full 128-bit ID and `FileAttributeTagInfo` for each held object; reject reparse objects.
2. Relative `NtCreateFile`: single component, `FILE_CREATE`, explicit protected owner-private DACL, `FILE_DIRECTORY_FILE | FILE_WRITE_THROUGH | FILE_SYNCHRONOUS_IO_NONALERT`; add `FILE_OPEN_REPARSE_POINT` in the production-candidate case. No delete-on-close or no-buffering. Share `READ | WRITE | DELETE`. Access: `DELETE | READ_CONTROL | SYNCHRONIZE | FILE_LIST_DIRECTORY | FILE_TRAVERSE | FILE_READ_ATTRIBUTES | FILE_WRITE_ATTRIBUTES | FILE_ADD_FILE | FILE_ADD_SUBDIRECTORY`. Record requested mask/options, raw `NTSTATUS`, I/O status and creation disposition, handle identity, owner/DACL and attribute results. Test collision, existing reparse, and denied access without following or replacing them.
3. Parent authority handle: traverse/read-attributes/read-control/synchronize with full sharing. Obtain and retain a separate parent commit handle with add-file/add-subdirectory/write-attributes rights, same identity, using native directory open. Compare minimal versus writable access for normal flush; do not weaken production authority based on a passing unrelated handle.
4. Run direct-create and staged-rename cases. Rename with `SetFileInformationByHandle(FileRenameInfoEx)`, flags `0` (no replacement), held destination `RootDirectory`, counted UTF-16 single component. Record success/error, held and relative-name identities before/after, and competing reader observations. Test held source, held parent, and an intentionally open descendant separately.
5. Normal-flush the retained child and commit-parent handles via `NtFlushBuffersFileEx(handle, 0, NULL, 0, &iosb)`. Record export availability, status, I/O status, latency and repeat results. Compare Win32 `FlushFileBuffers` diagnostically; do not silently substitute a weaker variant. Exercise repeated flushes on the identical handles after an injected reported commit failure. Real native I/O failure/recovery needs a disposable VM/storage fault fixture.
6. Crash checkpoints: after create, rename, child flush, parent flush, and acknowledged success; include multiple missing ancestors followed by a durable payload. An external controller must abruptly power off the disposable VM or storage fixture without graceful flushing, then inspect names, identities, DACLs and payload. Record host cache/power-loss limitations. Process termination only tests cleanup/restart, not power loss.

## Failure and retry contract

Before publication submission, clean only the owned private empty stage. Disarm automatic deletion before rename submission. Unresolved rename failure is `PublicationUnknown`; reconcile by held-parent name lookup plus full held-child identity under the service lease, never by blind rename retry. Successful final create or rename followed by flush failure is `PublishedDurabilityUnknown`: retain child and parent commit handles, perform no deletion/rollback, and retry only the outstanding flush sequence. Repeated successful flush is intended to be idempotent; verify that on the target OS. Closing the guard loses in-process retry authority; restart requires normal identity/privacy admission and explicit reconciliation.

Remaining uncertainty is narrow: native user-mode directory flush availability/access, exact no-follow option compatibility, namespace metadata coverage, and reliable commit retry after real I/O failure. The probe resolves operational questions; crash evidence and documented-contract review determine qualification. Lack of explicit prose is neither proof of impossibility nor permission to report durable success.

## Consumer constraint to resolve before Task 4 implementation

Fresh source inspection of `app-state/src/lib.rs::sync_directory_chain` and `canonical_directory_sync_failure_is_retried_even_when_ancestors_exist` confirms that retry currently rechecks the complete chain even after failed creation leaves every directory present. The retry test also verifies failure after document bytes become visible does not report success. A future native implementation must preserve those semantic obligations.

The proposed `provision_directory(path, privacy)` API does not yet encode how an externally durable anchor is established across restart. Directory existence alone cannot discharge an earlier uncertain creation. On Windows, requiring writable commit handles for every pre-existing ancestor up to the volume root may demand authority the app/service does not have. Before implementation, specify the anchor/reconciliation evidence and test it with an ordinary user token; do not solve this by widening privileges, silently omitting an uncertain ancestor, or treating AlreadyExists as durable. This is a concrete contract issue for Task4's design gate, separate from whether a native flush call succeeds.

### Probe binding availability checked locally

The installed pinned `windows-sys 0.61.2` already declares user-mode `ntdll.dll` bindings for `NtFlushBuffersFile` and `NtFlushBuffersFileEx` under `Wdk_Storage_FileSystem` with the existing Foundation/System_IO types. The probe therefore does not need a new binding crate or dependency version. This is SDK binding evidence only: it does not prove export availability or successful directory operation on a native host. Preserve the required runtime export/status/access observations.
