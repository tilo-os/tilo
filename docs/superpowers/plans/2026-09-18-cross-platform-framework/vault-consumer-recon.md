# Vault consumer source refresh before Task7

Read-only source inspection; no accounts product changes or tests run. Task4 Unix provisioning is still under implementation. This document identifies concrete decisions required before the executable consumer brief.

## Production path and required migration

The owner is `crates/system/accounts/src/vault.rs`, not the Passwords app. `SecretVault::try_save` creates the directory through create_dir_all, obtains a custody-selected key, serializes the entries, seals them and writes vault.enc through atomic_file::write. It returns Result<(), String>; accounts secrets.rs callers propagate failure before publishing dependent account state. Preserve that ordering and public result compatibility while retaining useful native phase diagnostics.

`local_file_key` reads ambient vault.key with unbounded fs::read. Correctly sized data is accepted without owner/ACL/link checks; malformed data is refused. Every read error currently generates a fresh key and replaces the old path through write_with_mode(0600). Task7 must allow generation only for proven NotFound; all other read/admission failures preserve the original file and fail. Use held bounded validated read and OwnerOnly IfAbsent. An actual collision must discard the losing generated bytes and select the validated winner. Do not emit generated key bytes after any uncommitted creation.

The ciphertext envelope is QASV + version1 +24-byte nonce + XChaCha20-Poly1305 data. Key length is32. Keep formats, location, nonce generation, zeroizing buffers and app-facing custody unchanged. The existing tests vault_put_save_load_round_trips and key_file_is_owner_only are explicit baseline checks; later tests must use try_save where observing success/failure matters, rather than treating the log-and-swallow save wrapper as success evidence.

## Shared existing-winner requirement

A matching existing key after a dropped publication error has the same durability problem as Task5's existing claim winner. Reading32 valid bytes does not prove the prior namespace commit. A known owned commit error can retry its retained handle; collision/restart must establish the required existing file and parent obligations through a shared native contract. Coordinate with Task5 design rather than adding another fsync/open implementation inside accounts. Replacing an existing key to obtain fresh-publication evidence is forbidden: it can strand ciphertext and violate concurrent custody.

## Existing-directory compatibility requires an explicit decision

Current saves create the vault directory with create_dir_all and ordinary inherited permissions. Existing vault roots may therefore be0755 even when vault.key is0600. The new provision_directory(OwnerOnly) deliberately rejects an existing non-private requested leaf and never chmods it. Wiring that policy without a migration decision would make those existing vaults unusable for saves. Do not weaken OwnerOnly validation or silently rewrite ACLs to make old fixtures pass. The Task7 design must specify the supported legacy-directory admission/migration behavior, distinguish name confidentiality from protection against foreign mutation, and verify real old-format/key-directory fixtures. Required compatibility cannot be waved away as successful extraction merely because refusal is safe. This issue needs resolution before implementation, alongside the trusted namespace premise of publication.

## Custody boundary

SecretService lookup failure already refuses local fallback. Its migration path separately reads a local key, stores/verifies it remotely and removes the local path. That is existing source behavior, not proof of safe held-file custody or cross-platform transport. Task7 must avoid introducing a second weakened local-key read route; any helper reuse must preserve selected custody and errors. A full SecretService/Keychain/Windows credential service port belongs to the separately tracked credential unit; do not claim it from storage migration or expand this task into an unreviewed transport redesign.

Required tests remain first save/reopen under absent roots, actual separate-process no-replace contention choosing one durable key, malformed/private-invalid/denied reads causing zero regeneration, uncertain key publication preventing vault encryption/publication, format-compatible ciphertext reopen and downstream metadata not published on error. Native Windows directory/bootstrap and cross-principal evidence remain open. Settings-store's actual parent-barrier tests are being implemented in Task4; Task7 should reuse that evidence and add only uncovered file-phase/format caller checks rather than rerun a redundant broad suite.
