# N02 private-cache extraction reconnaissance

Source-only snapshot, 2026-09-18. No product edit, build, test execution, package operation or git mutation was performed. This is a bounded ownership/API recommendation, not an executable implementation plan or native qualification. N02, S01/S02 and L02 remain open.

## Finding and current boundary

The smallest coherent cache authority is **`internal_cache.rs` plus all eight child files**, together with the native held-component verifier currently embedded in `internal_bundle.rs`. Moving only the Linux and Windows files would expose their provider/session preparation authority to the app or leave a framework-to-app dependency. A small portable selection/format/transport dependency split is unavoidable; it must not turn metadata into a caller-constructible authentication or ownership proof.

The approved N03 transfer already owns destination security, no-follow operations, migration stores/journals and connected-folder mechanisms in `crates/system/folder-service`. They are **not** new extraction inputs. The public [relocation report](connected-folder-relocation-report.md), [review](connected-folder-relocation-review.md), and [source manifest](connected-folder-relocation-source-manifest.json) establish that boundary. Independently checked 70 relevant manifest entries: all current folder-service files in that manifest and selected old migration/security/no-follow tombstones match. This checks source identity, not the reported native results. `folder-service/src/lib.rs:25` keeps these modules private. Do not add a cache dependency on their implementation modules or widen their visibility. A later common-native consolidation requires a separate ownership handoff; this reconnaissance changes none of them.

The original audit's A05-06/A05-07 remains useful for invariants, but its old migration/security app paths are historical. Current N02 work consists of the residual cache/verifier boundary and remaining storage/location consolidation, rather than redoing N03.

## Proposed ownership and semantic API cut

Use one focused **headless installer-artifact service**, exposed to apps through `tilo-app`/`ui`, with cache, checkpoint, worker and held verifier as private modules. This is an ownership name, not a proposed parallel general filesystem or permission service. Native durable publication/privacy/lease mechanisms converge on **existing `atomic-file`** as equivalence is proved; current cache admission and protocol checks must not disappear to make that convergence convenient. Do not put Imager release/boot policy into atomic-file or folder-service.

The smallest reviewable relocation can keep current algorithms and divide that service into portable artifact data/authentication/transport modules and private native storage modules. Extract only the necessary internal-release representation/authentication slice from `release.rs`; retain the current portable HTTP/range/hash algorithms and bundle format rules as portable modules, not native backends. A separate portable packaging-format crate is an optional later sharing choice, not a prerequisite or excuse to pull the full release module into framework code. App release offering, selected architecture, setup experience, strings and preference schema stay app-owned. This physical location recommendation extends A05-07's original portable/native separation; it does not reclassify portable algorithms as platform mechanisms.

Proposed app-facing operations are the current semantic vocabulary: obtain available release descriptions/opaque selections, start or resume the selected download, observe coalesced status, pause, cancel, release held readiness, and explicitly discard validated partials. Keep operation identity and selection binding in opaque tokens; retain committed bytes per role, final presence, residue and uncertainty separately. A semantic feature must not let app code choose Linux/Windows providers or construct a native root. Unsupported capability is a result, including on current macOS production hosts, not an app cfg fallback.

The eventual trusted host composition supplies the existing package/principal/workspace/instance lifetime and catalog trust source. The app chooses a catalog entry; it does not submit an arbitrary digest/URL struct and call it authenticated. Required release/selection proof constructors remain private. Existing signed-application catalog provenance must remain explicit: embedded bytes in a development build are not a signature. The precise host catalog-admission API is an **open design choice** below; no new permissions registry is proposed.

For consumption, keep the current worker-held scoped reader contract: a borrowed cancellation view and two borrowed read/seek interfaces, no `File`, cloned handle, native ID constructor or cache pathname. Ready remains private. The current app need not expose consumption at all while staging is unavailable; a future authorized installer gets an internal framework handoff rather than a raw app handle bridge. One-shot local-bundle verification takes validated metadata and an authorized directory input and returns verification-for-this-call, not stable byte authority. A compatibility path entry, if retained during G02, must remain explicitly weaker than a completed host grant integration and revalidate on each operation.

Keeping all existing transport code physically app-side is an alternative, but it requires a new scoped transfer adapter that cannot manufacture `PreparationComplete`, claim a durable acknowledgement or escape the prepared file borrow, plus separation of coordinator authentication. That is a larger authority/API rewrite than the proposed cohesive move. Do not choose it merely to preserve current module paths.

## Invariants and compatibility that extraction must preserve

**Storage authority.** One retained root lease covers both components and survives either partial/final owner. Root contents are exactly the permanent lock, payload directory and two distinct journal parents. Acquire validates existing entries without repairing unknown or unsafe residue. Linux holds a no-follow ancestry chain, checks owner/mode/ACL snapshots, ordinary single-link files and ext4/XFS/Btrfs semantics (`linux.rs:167–264,325–451`). It explicitly protects a cooperative current-user boundary, not hostile same-UID or privileged mutation; check-then-unlink/rename is not atomic identity-conditioned mutation. Windows retains native ancestry, DACL/identity snapshots, local disk and NTFS/ReFS admission, native UTF-16 names, reparse/type/link refusal, alternate-stream name refusal and sharing constraints (`windows.rs:282–459,751–938`). Do not normalize raw Unix bytes or unpaired UTF-16 into lossy strings.

**Checkpoint persistence.** Preserve root `qos-internal-install/<manifest-sha256>`, `ownership.lock`, `payload`, `journal-0`, `journal-1`, working `.qos-part-<32 lowercase hex>` names, identity digest domains `qos-linux-dev-ino-v1` and `qos-windows-volume-fileid-v1`, and exact record encoding. `checkpoint.rs:166,228` binds length-prefixed manifest digest/role/filename/component digest plus index and size; `QOSCP001` contains little-endian generations/epochs/lengths, ownership digests, prefix digest and checksum. No native identity is reconstructed as authority from those decoded fields. Preserve bounds: 64-MiB intervals, 4096-byte maximum record, 16 scan entries, 16 create collisions, at most three survivors, at most two retained committed records, generation cap `u32::MAX`, three transport attempts and 1-TiB component bound.

**Preparation and recovery.** Fresh creation is settled with zero ownership before cooperative cancellation can abandon it (`checkpoint.rs:113`). Only successful `Session::prepare` issues the private receipt: revalidate ownership, validate bounded history, independently read/hash surviving prefix and retained current-epoch digests, normalize only known survivors, trim only authorized uncommitted tails, restore cursor, observe cancellation, then mark prepared (`:388–505`). Reset fence is published before destructive truncation. Publication uncertainty poisons the current operation and requires fresh authenticated reacquisition; decoded hints and caller booleans do not clear poison. Bootstrap authenticates finals independently before classifying stale partial evidence. Both partials are prepared before the first payload transfer (`coordinator.rs:467`).

**Publication and durability.** Independent streaming/readback hashers must remain independent; data flush/sync and readback precede acknowledgement (`checkpoint.rs:605,685`). Linux journal namespace changes are synced, final publication requires actual `RENAME_NOREPLACE` without fallback, the held bytes are reverified after rename and payload parent synced before old evidence is retired (`linux.rs:915,1029`). Collision accepts only an independently authenticated winner. Failure after publication may leave a final plus old evidence; never roll back or report that nothing changed. Windows `namespace_boundary` is only a snapshot validation, explicitly **not a directory durability barrier** (`windows.rs:1543`). File flush ordering is not a power-loss persistence guarantee. Native flush errors and cleanup uncertainty remain observable; S01 qualification is still needed.

**Consumption and worker lifetime.** `with_verified_reader` re-verifies at actual consumption, retains guards through callback failure, restores cursor, and runs held/root/cancel postchecks without short-circuit (`internal_cache.rs:23`; native methods above). Coordinator token selection/operation IDs reject stale controls; replaced requests cancel old work out of band; drop cancels and joins (`coordinator.rs:119,290`). Cancellation does not erase committed bytes, final presence, residue, boundary error or uncertainty. Filesystem calls and a consumer callback remain cooperative with no bounded cancellation latency promise. HTTP connect/read bounds are 10/30 seconds, not a whole-object deadline (`internal_download.rs:113`). Do not report a generic Cancelled outcome as clean rollback.

**Bundle verification.** Preserve exact length plus EOF and SHA-256 checks; retain all component handles until all name/identity checks finish; reject aliases and changed earlier components; revalidate directory binding; preserve cancellation checkpoints (`internal_bundle.rs:388–525,853–891`). Current Unix directory open refuses a symlink at the directory leaf but is not the Windows full explicit ancestor walk; do not describe them as identical guarantees. This verification is not provenance, filesystem qualification, boot proof or retained install authority. Portable closed schema, boot/EFI rules, duplicate/unknown-key and object-shape rejection remain independent of host native implementation.

**Location and preference persistence.** Linux uses nonempty `XDG_CACHE_HOME` or home `/.cache` with raw absolute-ancestry validation (`linux.rs:361`); Windows uses `dirs::cache_dir` (`windows.rs:853`). Keep those old roots discoverable until L02 has an explicit migration and concurrent-upgrade policy. Current product preference is `data_local_dir/qos/setup/internal-download-selection.json`, schema 1 (`internal_download_flow.rs:15,668`); its saved key is reselected against the current catalog, not authority. Its current save at `:713` creates parents, persists a tempfile and ignores directory-open/sync failure at `:734`. This is a concrete remaining storage consolidation issue, not a guarantee to preserve or a claim the cache protocol covers preference persistence. Route the mechanism through existing storage with honest failure phases and preserve JSON/path compatibility.

## Decisions still needed before an implementation plan

1. **Portable authentication boundary:** settle the headless service/portable format location and how trusted host catalog admission returns opaque release selections while retaining app-owned offer policy. Do not expose `InternalRelease`/`SelectedManifest` constructors accepting arbitrary asserted trust. Moving just the nine cache files cannot resolve this safely.
2. **Primitive consolidation boundary:** explicitly map cache ownership/snapshots, journal publication and final no-replace transfer onto existing atomic-file capabilities. Preserve missing operations privately until equivalent shared primitives exist. Native-chain changes belong to their assigned owner after formal handoff; folder-service stays untouched.
3. **Error contract:** map existing String errors plus `uncertain`, committed-prefix and residue facts into framework typed results without losing multiple boundary failures. Distinguish permission, unsupported, busy, cancellation and published-but-unproven effects. Current worker phase alone is not enough.
4. **Host scope and lifecycle:** integrate existing HostContext and live collaborator authority/revocation without a parallel grant/identity registry; the current worker cancel/join contract is necessary but does not by itself satisfy that framework contract.
5. **L02 and preferences:** retain legacy cache and preference discovery, settle migration/concurrent-upgrade semantics, and fix honest selection-preference persistence through common storage. Do not silently move caches or use shared-temp fallback.
6. **Host guarantees:** choose whether the first delivery is source ownership only or includes new macOS cache support/Windows durable namespace work. The bounded move must keep current refusals and guarantee differences; it cannot close the original N02/S01/S02/L02 acceptance by relabeling code.
