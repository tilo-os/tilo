# Sidebar Wheel Disc — Design Reference

This doc captures the **wheel-disc** widget that replaced the original
`SidebarWheelChrome` as the live shell's left-side navigation. The
earlier concept's 96 px permanent sidebar
— `absolute left-0 top-0 bottom-0 w-24 z-40`) is superseded by an
in-plane circular disc. This is a **deliberate deviation** from the
concept, mandated by the user's 2026-04-21 spec.

## Origin and spec

### First statement (2026-04-21)

> "I want a rounded, wheel like thingy on the left, placed on the same
> plane as actual windows (a strip should be an axis going out from that
> middle → basically a big circle). You can then drag this wheel in the
> middle to move it to another strip of windows."

### Clarification (2026-04-21, same day)

> "No permanent sidebar, but workspaces appear as rotated axes of the
> wheel disc, meaning you can go to the left and drag it to move
> between workspaces."

**Authoritative reading:**
- The disc is a **single widget occupying an in-plane slot** at the left
  of the workspace content — not a floating overlay, not a column.
- Each **workspace** is one **spoke** radiating from the disc centre.
- User drags the disc's body (any press, any position inside the disc)
  → disc rotates → on release, snaps to the nearest spoke → that
  spoke's workspace becomes active.

### What the concept had, and why we diverge

| Element | Concept (`DesktopView.tsx`) | Tilo shell (disc) |
|---|---|---|
| Placement | `absolute left-0 w-24 z-40` (floating overlay column) | In-plane left leaf of the content column |
| Size | 96 px wide, full viewport tall | 240 px square (diameter), vertically centred |
| Shape | Rounded card stack | Circular stroked rim |
| Workspace representation | Vertical list of cards | Radial spokes |
| Interaction | Click a card / scroll to switch | Press-drag-rotate, release snaps |
| Active cue | Pill fill + indigo ring | Rim arc glow at active spoke's angle |
| Collaborator dots | Per-card presence dots | Up to 3 per-spoke presence dots outside the tip label (commit `4ffb786`) |
| Plus button | "+" card at tail | Plus-button slot below the hub; press appends + activates a new workspace (commit `dc8956a`) |

### Interaction model

```
press(inside disc) → drag_from = cursor, drag_rotation_origin = rotation_deg
move                → rotation_deg = drag_rotation_origin + dy * deg_per_pixel
release              → snap_to_nearest():
                           nearest_offset = round(rotation_deg / spoke_gap)
                           rotation_deg   -= nearest_offset * spoke_gap
                           active_idx     += (-nearest_offset) mod n
                       drag_from = None
```

- `deg_per_pixel()` = `(180/π) / (diameter_px / 2)`. For a 240 px disc,
  ~0.48 deg per pixel — a full-diameter drag sweeps through ~115°.
- Snap math uses **integer rounding on the signed offset**, so a tiny
  accidental drag does NOT change `active_idx`: only crossing the
  half-gap does. This matches the "dead zone" a physical knob would
  have between detents.

### Draw layers (pure Vello)

1. **Outer rim** — `Circle(cx, cy, r)` stroked 1 px in `neutral[3]`.
2. **Active-spoke arc** — 24° translucent stroke at 6 px width, coloured
   `accent[5] @ 0.3`, centred on the active spoke's angle.
3. **Spoke labels** — one `Text` per spoke, 24 px inside the rim,
   rotated to read along its ray. Active label is `text_primary`; the
   rest are `text_dim`. **Readability flip** (planned in-flight): for
   labels where the spoke angle lands between 90° and 270°, add π to
   the rotation so the glyph is not upside-down.
4. **Hub dot + crosshair** — 4 px filled circle in `text_dim` + two
   3 px perpendicular strokes in `text_primary` at the disc's centre.
   Reads as a grabbable control.

### State

- `spokes: Vec<SpokeLabel>` — one entry per workspace. `SpokeLabel`
  carries the display `text` and an `Option<u64> workspace_id`
  correlator. The widget itself never dereferences the id; the host
  maps `spokes[active_idx].workspace_id` back to a `WorkspaceId` on
  snap.
- `active_idx: usize` — which spoke is "up".
- `rotation_deg: f32` — free-running visual rotation. Snapped to a
  multiple of `spoke_gap_deg()` on release.
- `drag_from: Option<Point>` — present iff a drag is in progress.
- `drag_rotation_origin: f32` — rotation at drag-start, anchor for the
  `dy * deg_per_pixel` mapping.

### Sign convention

Dragging **down** (positive dy) maps to **positive rotation_deg**. The
rotation sweeps the spoke set clockwise-visually; the *active* spoke
advances by `-nearest_offset`, so a full downward drag through one
spoke gap brings spoke index +1 into the active slot. The user's
mental model: *pull the wheel down to reveal the next workspace below*.

## Known gaps (as of 2026-04-21)

1. ~~**CRDT write-back**~~ — **resolved in `65d105d`**. The widget
   now takes `Rc<RefCell<ChromeState>>` via `with_chrome(...)` and
   calls `chrome.borrow_mut().tree.set_active(ws_id)` on snap. Tested
   by `snapping_publishes_to_chrome_only_when_the_workspace_changes` (phase `snap_publishes_active_workspace_to_chrome`).

2. ~~**Label readability**~~ — **resolved in `65d105d`**. Labels whose
   spoke angle lands in (90°, 270°) get an extra π rotation so glyphs
   stay upright.

3. ~~**Collaborator presence on spokes**~~ — **resolved in `4ffb786`**. The disc now queries `PresenceCtx::peers_on(PresenceKey::Workspace { id })` for each spoke and renders up to 3 per-peer dots 16 px outside the tip label, tangent to the rim. Colours come from `PresenceCtx::color_for` so palette pins survive.

4. ~~**Plus button**~~ — **resolved in `dc8956a`**. The disc now renders
   a dedicated Plus slot below the hub; pressing inside it calls
   `ChromeState::add_workspace` which appends a new workspace and sets
   it active. Covered by
   `sidebar_wheel_management_button_creates_workspace`.

5. ~~**Animations**~~ — **partially resolved in `7916273`**.
   On release the disc now springs `rotation_deg` toward the snapped
   target using the `snappy` preset (stiffness 260, damping 28 — close
   to the concept's 200/25). `active_idx` and the CRDT write-back still
   commit synchronously at release time; only the visual rotation eases.
   Grabbing the hub still feels instant (no ease-in) — keeping that gap
   open is intentional: physical knobs don't ease *into* drag. Covered
   by `drags_and_clicks_settle_on_a_spoke` (phase `snap_animates_rotation_over_multiple_ticks`).

## Removing the old sidebar

`SidebarWheelChrome` (`crates/session/shell/src/shell/sidebar_wheel_chrome.rs`)
is **no longer mounted** in the live shell. The module file is kept in
tree for reference and because older tests may still reference its
types. A future cleanup can delete the module once we are confident
the disc is correct and no test uses it.
