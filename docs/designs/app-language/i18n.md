# Words and their translations

Every word a tilolang package shows a person is a message: the text in its views, what the app
is called, its actions' labels, what its types and fields are called, its enum cases, its
filters' labels and the first sentence of each doc comment. The package writes them once, in its
source language, where they belong. Tilo shows them in each reader's language, and a translation
never asks for a change to the package's code. There is no new syntax and no key written by hand.

## 1. One mechanism

Native apps already keep their words in Fluent catalogues (`locales/<lang>.ftl`, resolved by
`ui-core`'s `i18n` at draw time). A tilolang package uses the same catalogues and the same
resolver. The only difference is where the source catalogue comes from: the compiler writes it
from the source into the package's module, so nobody keeps it by hand and no copy of it is
committed. `tilolang catalogue <package>` prints the same words, for a translator or an agent.

## 2. What a message is, and its key

| What | Source text | Key |
|---|---|---|
| A declaration's name as people read it (type, field, enum case, action, view) | its `label:`, else its name in words | `<id>` from `app.ids` (`mavvhka7`) |
| Its description | the doc comment's first sentence | `<id>.doc` |
| A type's noun | its `noun:`, else its name in words, one of it and several | `<id>.noun`, one Fluent message with `$count` |
| What the app is called | the title its `app` declaration gives | `<id of the app>` from its app id |
| A filter's label | its label, or its field's name in words | `<id of the type>-filter-<snake key>` |
| What an action's parameter is called where a person gives it | its `label:`, else its name in words | `<id of the action>-<name>` |
| Text in a view | the string literal | `<id of the view>.<slug of the literal>` |
| Words a `fn` returns where a view shows them | the string literal | `<id of the fn>.<slug of the literal>` |
| An action's label that follows its target, why it cannot run | the string literal | `<id of the action>.<slug of the literal>` |
| Words code writes into a resource (`std.say("Morning: {n} done")`) | the string literal | `<id of the action, view or fn>.<slug>` |

- **Declarations are keyed by their stable id,** so renaming a field in code keeps its
  translation, the way it keeps its data.
- **A parameter is named where a person gives it.** Its name in words is what a form or a
  consent sheet shows beside the value ("At: 2:30"), and a name that reads as something else
  when its value stands beside it says what it holds instead:
  `saved: Bool (label: "On the watch queue") = not queued(yt, v.key)` reads as "On the watch
  queue: yes". The parameter's name is still the name its argument is recorded by, so the
  label changes the words and never the format of an invocation. A field takes the same form
  (`saved: Bool (label: "Kept in your places")`), so the words a person reads of it come from
  the catalogue while its stored name never changes.
- **A part a view composes is not a declaration.** The row view a loop body becomes stands in
  its view: it takes that view's name, shows its item's fields' own messages, and has no
  message of its own. So no name in a catalogue is built from a binding: a screen reader says
  words, never one letter of one.
- **A view's literals are keyed by the view and the text itself,** so moving a line inside a
  view keeps its translation. Changing the English text makes a new message; the old
  translation is reported as stale, never shown for the new text.
- **Only words a component shows are messages.** A literal is a message where a component's
  text prop shows it: the value given, or what that value takes from an `if` or `match` branch,
  `.some(...)`, a list or a `let` that keeps it. An author never has to know where the words
  were written: a literal a `let` holds, one a branch chose, and one handed to another view's
  `Text` parameter are the same message, keyed under the declaration that writes them. A prop
  the toolkit declares as data (`#[component(data)]`: a key, an address, an emoji) takes its
  literal as text, and so does a literal a view compares or passes to a function. A `std` view
  that takes a `Text` and shows it (`std.composer(state, "Say something", send)`) shows the
  words given to it, so that literal is the calling view's message too: a sentence is
  translated where it is written, not by the view that lays it out.
  An action's `label: if pinned { "Pin" } else { "Unpin" }` and the reasons of its `require`
  and `applies` lines are words too, attributes of the action's own message wherever a view
  applies it.
- **Words code writes into a resource are `std.say("...")`.** A title an action gives a resource it
  makes ("Morning: 3 done"), a status a `fn` answers: a literal that reaches no prop of words
  may be data (a tag, a query, a key), so the author says which are words. `std.say` makes its
  literal a message of the declaration it is written in, its interpolation an argument, read in
  the language of whoever runs the code: the person who pressed the button reads the note in
  their language. A view needs it only where its words reach no prop, `let` or parameter at all:
  a `fn` whose result a view shows is part of the view's words, so the literals its body returns
  are messages of that fn's own declaration (`answer_words(a)` in a view's text), and one no
  view shows writes none.
  It is the library's word (`stdlib::NS`), never a bare one: `say` is a verb an app takes for an
  action of its own, as a chat app's is ("Say something"), and no built-in name may take it. A
  view's message key is an attribute of the view's own message,
  `d-<view id>.w-<slug>`, since a Fluent name has no dots; two texts of one view with the same
  slug are numbered.
- **Interpolation becomes Fluent variables named after what is interpolated:**
  `"{t.count} new"` is `{ $count } new`. Plurals, grammatical gender and word order are the
  translation's business (Fluent selectors). A type's noun is one of it and several as English
  writes them, and the derivation knows a name that already names several (`Tasks` is a `task`
  and `tasks`) and English's irregular plurals (`Person` is a `person` and `people`), so a noun
  the app words its own way says it: `type Pinned (noun: "pinned app")` is one `pinned app` and
  several `pinned apps`, and `type Notebook (label: "Notes")` is read as `Notes` where its name
  in words would say `Notebook`. An action whose words say how many writes the count in its
  `did:` and the sentence for several in `did_many:` (`did: "wrote a message", did_many: "wrote
  {count} messages"`), so history reads "wrote 7 messages" in one sentence rather than a count
  beside it. `did:` names the action's arguments as any words do (`"made {zone} the active
  zone of"`), and chooses its words by one of them with `if`/`else` over a `Bool` or a `Text`
  compared to a word, or `match` over an enum (`did: if on { "turned on the rule" } else {
  "turned off the rule" }`): a Fluent selector over that argument, which a translation words
  per case. A change keeps only the arguments its record holds once written, so the words of
  one that removes what it names say less (`"stopped allowing a service in"`). The words also
  read a field of the changed record as the change found it and left it: `did: "set the limit
  from {limit.before} to {limit.after}"` (`{ $limit_before }`, `{ $limit_after }` in a
  translation). History reads those values from the record's own history when it is read, and
  stores nothing beside it: a reader sees `before` only if they read the record both before and
  after the change, so one the change let in sees `after` alone; a field declared `(secret)`
  (`code: Text (secret)`) never shows a value, and a record kept on one device (`readers: author
  here`) has its history there alone. An action that declares no `did:` and changed one field
  says that field's change ("Changed limit of Spare keys to 7"; a secret one "Changed code of
  Spare keys"); otherwise it reads by its label ("Ran “Allow a service” on public"), never by an
  id.

### Restoring a history sentence

A ported app's history sentence is restored on the action that makes the change, never on a view:

1. Find the action that writes the field the old sentence described (`tilolang catalogue
   apps/tl/<app>` lists each action's id as `d-<id>`).
2. Give it `did:` in the source language, after who did it and before the resource's name:
   `did: "turned on the rule"` reads "Turned on the rule “https”". Name an argument (`{zone}`)
   when the record still holds it after the change; read a field's value with `{field.before}` /
   `{field.after}` when the argument does not reach the record (a name it picks a field by, a
   count it adds); choose words with `if`/`else` or `match` over a flag, a word or an enum.
3. Mark a field `(secret)` when its value must never be shown (a password, a token, a key).
4. Translate the `.did` attribute in `locales/<lang>.ftl` under the action's `d-<id>` message; a
   choice is a Fluent selector over the same argument (`{ $on -> [true] … *[other] … }`), and the
   German sentence is said before the resource's name (`schaltete die Regel ein: „https“`).
5. Prove it with a test through `Pane::history` (or `history_as` for another reader) in the
   app's test file, in English and German, then mark the parity row "replaced: `d-<id>.did`,
   proof `<test>`".

## 3. Build and check

`tilolang build` writes the source catalogue from the package's sources into its module, the way
it keeps `app.ids`, and commits no copy of it: `tilolang catalogue <package>` prints the same
words, which is where a translator and an agent read them. Translations are `locales/<lang>.ftl`
beside the sources, and a translation has every word of its source and no more: `check` reports
a key a translation translates that the source no longer says, and a word of the source a
translation lacks. `check` reports too a view whose name reads as code rather than as words
(`note_editor_for_t` is "Note editor for t", the last word a binding a screen reader reads out on
its own). A package ships its catalogues with its module, and the source one the module carries is
always the one its sources write at that build.

## 4. Who resolves, and in which language

Words are resolved by whoever shows them, in that reader's language, at the moment they show
them:

- **The published tree carries keys and source text:** a resource's and action's labels, nouns
  and descriptions. It never carries one reader's translation. A resource shared between
  people reads in each person's own language, as history's sentences already do
  ([resources.md](../../architecture/resources.md) §5.2). A tree is published and read in one
  process, so the resource layer names a resource through that process's catalogue while it
  publishes it (`tilo_resource::label`): the declaration's text is the key's source, and a
  catalogue without the key names the resource by that text.
- **Views resolve at draw time** through the package's catalogues in the person's locale,
  falling back to the source text.
- **A window speaks one language.** Its language is chosen once, when the package loads, from
  the person's preference against the languages the package ships: the person's when it ships
  it, the package's source language otherwise. The toolkit's own words and the platform's date
  and number formats follow that same language
  (`ui::i18n::speak_window_language`), so a package written in one language reads in that
  language throughout, its frames and dates included, rather than mixing its own copy with the
  desktop's. Only the window's own catalogues say which languages it ships: the toolkit's
  labels and the Settings index are in every window and ride along in its language, so a word
  only they carry in the person's language reads in the source language inside a window that
  does not ship it. A process presents one window, so the language is the window's. A host that
  draws several windows in one process (the tilolang process of a workspace and author, the shell
  with its slot views) picks each window's words and each window's language: the session names
  the person's language with every instance it hands over (`InstanceRequest::language`), so a
  host whose own process runs in another locale — a sandbox carrying only the variables its
  launcher had — still reads every word of a window from the catalogue in the window's language.
  A language the person chooses in Settings later is said on the host's action API with their formats
  (`Locale`), and every window it draws relabels where it stands. The launcher names the same
  language as the messages' locale of every app it starts, so a window's own chrome speaks it
  from its first frame.
  Words a process reads for another window — a development session seeding the demo apps, a host
  reading a package it does not present — are shared ones too: they read in the person's language where the
  catalogue carries it, and the language they are written in never becomes the process's. A
  window with nothing of its own to say — a system menu, a sheet of frames — reads the
  toolkit's labels in the language selected for the process, which is the person's.
- **Search matches every language the person reads.** A type's noun, its plural and its app's
  name match in the person's locales and in the source language, so "meine Mails" and "my
  mails" both find Mail.
- **Agents get the source language,** plus the person's locale to answer in.

Numbers, dates, durations, money and lists are never words in a message: they go through
`ui::format` with the reader's locale, as they already do. A day or a moment interpolated into
text (`"{t.title} due {t.due}"`) reads as the person's own dates do (`Jun 29`, `Jun 29, 2025`,
`Jun 29, 6:00 PM`), and `d.iso()` / `t.iso()` is its stored text for a machine.

## 5. What this replaces

- **`noun "…" "…"` (removed):** a type's noun and plural are the `<id>.noun` message, and the
  words it holds are the type's `noun:` option.
- **English-only `meta(r).noun` and `.plural`:** they resolve in the reader's locale.
- **Labels published as finished English strings** in `ActionSpec` and `ResourceType`: they
  carry their key beside the source text.
