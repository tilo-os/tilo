# Words and their translations

Every word a tilolang package shows a person is a message: the text in its views, its
actions' labels, what its types and fields are called, its enum cases, its filters' labels and
the first line of each doc comment. The package writes them once, in its source language,
where they belong. Tilo shows them in each reader's language, and a translation never asks
for a change to the package's code. There is no new syntax and no key written by hand.

## 1. One mechanism

Native apps already keep their words in Fluent catalogues (`locales/<lang>.ftl`, resolved by
`ui-core`'s `i18n` at draw time). A tilolang package uses the same catalogues and the same
resolver. The only difference is where the source catalogue comes from: the compiler writes it
from the source, so nobody keeps it by hand.

## 2. What a message is, and its key

| What | Source text | Key |
|---|---|---|
| A declaration's name as people read it (type, field, enum case, action, view) | its `label:`, else its name in words | `<id>` from `app.ids` (`mavvhka7`) |
| Its description | the doc comment's first line | `<id>.doc` |
| A type's noun | its name in words; plural derived | `<id>.noun`, one Fluent message with `$count` |
| A named filter | its label | `<id of the type>.filter.<snake label>` |
| Text in a view | the string literal | `<id of the view>.<slug of the literal>` |

- **Declarations are keyed by their stable id,** so renaming a field in code keeps its
  translation, the way it keeps its data.
- **A view's literals are keyed by the view and the text itself,** so moving a line inside a
  view keeps its translation. Changing the English text makes a new message; the old
  translation is reported as stale, never shown for the new text.
- **Interpolation becomes Fluent variables named after what is interpolated:**
  `"{t.count} new"` is `{ $count } new`. Plurals, grammatical gender and word order are the
  translation's business (Fluent selectors), and the source language's own catalogue may
  refine its message too: `{ $count -> [one] 1 message *[other] { $count } messages }`. So an
  irregular English plural ("people") is one line in `en-US.ftl`, not a keyword.

## 3. Build and check

`tilolang build` and `check` write `locales/<source>.ftl` from the source, the way they keep
`app.ids`: generated, committed, and checked so the two can't drift. Translations are
`locales/<lang>.ftl` beside it. `check` reports a translation key no message has, and a
translation older than its source text. A package ships its catalogues with its module.

## 4. Who resolves, and in which language

Words are resolved by whoever shows them, in that reader's language, at the moment they show
them:

- **The published tree carries keys and source text:** a resource's and action's labels, nouns
  and descriptions. It never carries one reader's translation. A resource shared between
  people reads in each person's own language, as history's sentences already do
  ([resources.md](../../architecture/resources.md) §5.2).
- **Views resolve at draw time** through the package's catalogues in the person's locale,
  falling back to the source text.
- **Search matches every language the person reads.** A type's noun, its plural and its app's
  name match in the person's locales and in the source language, so "meine Mails" and "my
  mails" both find Mail.
- **Agents get the source language,** plus the person's locale to answer in.

Numbers, dates, durations, money and lists are never words in a message: they go through
`ui::format` with the reader's locale, as they already do.

## 5. What this replaces

- **`noun "…" "…"` (removed):** a type's noun and plural are the `<id>.noun` message.
- **English-only `meta(r).noun` and `.plural`:** they resolve in the reader's locale.
- **Labels published as finished English strings** in `ActionSpec` and `ResourceType`: they
  carry their key beside the source text.
